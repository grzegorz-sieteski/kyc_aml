## 3. Decision route under D-24 (F1)

### 3.1 Order at the BFF

`POST /api/risk-profiles/{customerNumber}/decisions`. The BFF's own security layer runs first, then the request goes to the service:

1. **Session** (cookie, record, decryption). Failure: the constant 401 (the service's caller-not-identified bytes). No byte of the body is read.
2. **Origin**, then **CSRF**. Failure: 403. Only a caller with a session reaches this step, so an unidentified caller never sees 403.
3. **Forward** (3.2). The BFF judges nothing about the body: no size, form or content check, no 400, no 413.

v6 wrote "as BR-37 orders" for step 1. That was wrong: BR-37 orders the service's judgement of a decision. The BFF's order comes from D-24. (v4 5.4 cites BR-37 for the service identifying first; that citation is right and stays.)

### 3.2 How the body is forwarded (D22, D23)

- **Client:** the JDK `java.net.http.HttpClient`, HTTP/1.1, with the BFF's client certificate. It is in the JDK, so no dependency is added (copilot 0.1, 0.7). The JDK refuses a hand-set `Content-Length` ("restricted header name", probe), so the length goes through `HttpRequest.BodyPublishers.fromPublisher(publisher, length)`.
- **Declared length:** the client's `Content-Length` exactly as the BFF's Tomcat accepted it (`getContentLengthLong()`), unchanged, even when it exceeds 16 384. No declared length (chunked): `fromPublisher(publisher)`, sent chunked.
- **Stream:** the publisher reads the client's servlet input stream and stops after 16 385 bytes (`BoundedBody.DECISION_LIMIT + 1`). This bound never changes an answer: the service needs at most limit + 1 bytes to decide 413.
- **`Expect: 100-continue`** (`HttpRequest.Builder.expectContinue(true)`). The service's connector is set to `continueResponseTiming=onRead` by a `TomcatConnectorCustomizer` bean (`org.springframework.boot.tomcat.TomcatConnectorCustomizer`, present in `spring-boot-tomcat-4.1.2.jar`) calling `AbstractHttp11Protocol.setContinueResponseTiming("onRead")`. Boot has no property for it: its Tomcat metadata lists `max-swallow-size`, `max-http-form-post-size` and others, no `continue`. Tomcat's default is `immediately` (probe).
- **Why this meets D-24.** The service sends `100` only when `BoundedBody` calls `getInputStream()`, which `RecordComplianceDecisionResource.decide` does only after `identify()` succeeded and only when the declared length is within the limit (`BoundedBody.bytes`, read). Nothing before reads it: `DefaultBearerTokenResolver` has `allowFormEncodedBodyParameter` false, and `resolveAccessTokenFromBody` returns before `getParameter` when it is false (verified, offsets 1 to 36).

| Case | Service answer | Body bytes BFF to service (probe) |
|---|---|---|
| Not identified by the service, any length | Constant 401 | 0 |
| Identified, declared length above 16 384 | 413 `request-too-large` | 0 |
| Identified, chunked, more than 16 384 bytes | 413 after reading 16 385 | 16 385 |
| Identified, declared length at most 16 384 | Judged in BR-37 order | the declared length |

- **One refresh and one repeat after a 401** (v4 5.4) need no buffer: no byte was pulled from the client, so the repeat uses the same unread stream.
- **The BFF's own connector is also `onRead`.** A client that sends `Expect` gets `100` only when the BFF pulls the body, which happens only after the service's `100`.
- **Defence, not a path.** If a future service change sent `100` for a declared length above 16 385, the cut stream would end short of it and the JDK client would fail the exchange: the BFF answers `bff-unavailable` (503). That can only happen after identification.

The probe also shows why `Expect` and `onRead` go together: with Tomcat's default `immediately` and `Expect`, a 20 MB body ended in `IOException: HTTP/1.1 header parser received no bytes` at the client instead of 401 or 413. With `onRead` it answered 401 and 413 with no body bytes sent.

### 3.3 Malformed or duplicated `Content-Length`

- **Refused by the container, before any application code.** Two `Content-Length` headers (equal or different), a list (`5, 5`), a non-numeric value and a signed one (`+5`) are refused by `Http11Processor.prepareInputFilters` (`badRequest`: status 400, `ErrorState.CLOSE_CLEAN`, offsets 122 to 155; strings `multipleContentLength`, `nonNumericContentLength`). In the probe, neither the servlet nor a registered error page ran; Tomcat's `ErrorReportValve` answered with `Connection: close`. With `spring.web.error.include-stacktrace: never`, Boot installs that valve with `setShowReport(false)` and `setShowServerInfo(false)` (`TomcatWebServerFactoryCustomizer.customizeErrorReportValve`, verified). Deployment check: the BFF sets that property too.
- **What it reveals:** that the framing is malformed, nothing about the caller, the session or risk. No session is looked up and the BFF writes no log line. It is a container answer outside the application, in the same class as Tomcat's refusal of an oversized header, which the product owner accepted as LOW. The owner confirms this case (section 15 item 3).
- **`Transfer-Encoding: chunked` with `Content-Length`:** Tomcat drops the `Content-Length`, reads chunked and closes the connection after the answer (offsets 155 to 191; probe: the servlet saw -1). The BFF forwards chunked.
- The BFF's code never parses `Content-Length`. It reads `getContentLengthLong()` only after Tomcat accepted the header.
- **Residual:** an unidentified client with a large body and no `Expect` gets the constant 401 without the body being read; Tomcat then swallows up to `max-swallow-size` (default 2 MB) and closes. A client still sending may see a reset instead of the 401. That is container behaviour after the answer, and it reveals nothing.

### 3.4 Log line and correlation id (D-22, F14)

One line per request, `<time UTC ISO-8601> corr=<id> durationMs=<n>`, as v6 section 3, for every answer of section 4. The BFF generates the id itself (`UUID.randomUUID()`) and sends it to the service as `X-Correlation-Id`. A client's `X-Correlation-Id` is dropped: never copied, logged or forwarded. The service does not read the header today (no use in `src/main`).

The consequence for operations (the line cannot show success) is unchanged: section 15 item 1.

## 4. Refusals and answers on the decision route (F14)

- **Forwarded byte for byte from the service:** 200 (success, `RiskVersionResponse`); 400 (`request-not-readable`, D-12; kind not recognised, BR-32; justification missing, too short, too long or with a control character, BR-34; version viewed not valid, BR-33); 401 (only after one refresh and one repeat, v4 5.4); 403 (permission, BR-02); 404 (customer not found, BR-04; `request-not-handled`); 409 (changed since viewed, BR-33; changed concurrently, BR-30); 413 (D-09); 422 (critical fact, BR-36; already frozen, already escalated, nothing to clear, BR-35); any 5xx. Statuses read in `RecordComplianceDecisionResource` (`invalid` is 400, `rule` is 422).
- **The BFF's own:** 401 (no session, expired, decryption failure, Entra `invalid_grant`); 403 (origin, CSRF); 503 (`bff-unavailable`); 504 (`bff-timeout`).
- **The container's:** 400 for malformed framing (3.3).
- **Never from the BFF:** 400 or 413 about the body.

## 5. Redis: renewal cap, rotation and tag failures (F3, F11)

- **Renewal TTL.** The record holds `absoluteExpiresAt` in clear, set at sign-in and never changed by renewal or token refresh. Renewal computes `ttl = min(idleTimeout, absoluteExpiresAt - now)` with the BFF's clock and passes it to the Lua script (v5 section 6: TTL only, no value written, compare-and-set on the index). If `ttl <= 0`, the record and its index are deleted and the answer is the constant 401. A record therefore never outlives its absolute lifetime.
- **Retired-key period = the maximum absolute lifetime** (section 15 item 8). Every record under a retired key was written at or before the rotation, by a session that started earlier still, so it expires by rotation + absolute lifetime. Without the cap a renewal could push a record past that, which is why F3 mattered.
- **Unknown key id:** as v6 (record deleted, 401, one ERROR line with fixed text).
- **Tag failure under a held key:** record deleted and the constant 401. The first one in a process writes one WARN, `session record failed authentication under a held key; record deleted`, with no session id, key id or count. Later ones write nothing. A singleton `AtomicBoolean` gates the line. This replaces v6's "no line".
- **Tests:** 18.14 (renewal writes no value; both TTLs equal); **18.14b** (a session 10 s from its absolute expiry renewed with an idle timeout of 15 min: TTL 10 s; a request after the absolute expiry: 401, even though it was renewed); **18.14c** (`ttl <= 0`: record and index deleted, 401); 18.15 and 18.15b as v6; **18.15c** (two tag failures under a held key: two 401s, both records deleted, exactly one WARN with that fixed text and no digits).

## 6. Identity in the service (F5, F10, F16)

### 6.1 One chain per registered application (D24)

`CertificateSubjectResolver` (v6 6 step 1, unchanged) maps the certificate's registration to that registration's own `ProviderManager(new JwtAuthenticationProvider(decoder))`. There are four, `bff`, `us`, `gb` and `de`, each with its own `IdentityJwtDecoder`, `CachingJWKSetSource`, `FetchRecordingJWKSetSource`, `RateLimitedJWKSetSource`, `LastKnownKeySetSource` and `Health`, built by one factory method from the registration. A flood of unknown `kid`s on one certificate spends only that registration's budget (two admissions per 30 s window, v6 9.5).

An unregistered certificate gets the refusing manager: a `ProviderManager` over a decoder whose key source returns no keys (`(selector, context) -> List.of()`). No fetch happens, and our code contains no `throw`: the library refuses the token.

**Shared cases that remain:**
1. Every human user shares the `bff` chain. Users never present a token, the BFF does, and it presents only Entra-issued tokens, so a user cannot choose a `kid`. Only the BFF can spend that budget, and only on a real rotation.
2. The Entra key endpoint is one host for all four chains: up to 8 fetch attempts per 30 s. Whether Entra throttles this per client IP is to confirm in the tenant.
3. Health lines carry no chain name (BR-43 forbids caller identity in logs), so an outage writes up to four identical lines, one per chain per transition (v6 9.3 table, per chain).

### 6.2 Configurer (F16)

```java
.oauth2ResourceServer(resourceServer -> {
    resourceServer.addObjectPostProcessor(answerEveryFailure);
    resourceServer.bearerTokenResolver(headerOnly)
            .authenticationEntryPoint(notIdentified)
            .accessDeniedHandler(notIdentified)

```

`OAuth2ResourceServerConfigurer.validateConfiguration` (spring-security-config 7.1.2, offsets 58 to 79) asserts that with a resolver neither `jwt()` nor `opaqueToken()` is configured: "If an authenticationManagerResolver() is configured, then it takes precedence over any jwt() or opaqueToken() configuration." The `.jwt(Customizer.withDefaults())` in today's `BearerTokenSecurityConfiguration` would make startup fail. v6's "takes precedence" was wrong. The `rateLimitedKeySet` customizer goes with it (v6 7.6).

### 6.3 Claims and role, defined exactly (D16, D-15, D-19, D-23)

The validators read `Jwt.getClaims()` values with `instanceof`, never through `getClaimAsString`, `getClaimAsStringList` or the other conversion accessors. `ClaimAccessor.getClaimAsStringList` converts through `ClaimConversionService`, so a single string becomes a one-element list, and then calls `Assert.notNull`, which throws (verified). That accessor would both accept a single-string `roles` and throw from a validator.

- **`azp`:** a `String` equal, exactly and case-sensitively, to a registered client id. It selects the branch: the BFF's id gives the user branch; an onboarding id gives the app-only branch. Anything else refuses. The registration of `azp` must be the certificate's registration (test 18.4).
- **"`scp` present"** means the claims map contains the key `scp`, whatever the value: an empty string or an empty list counts as present. The user branch requires it present, the app-only branch requires it absent.
- **`roles`:** a `List` with exactly one element. That element is a `String` equal, exactly, to an `ActorRole` name of the branch: AML_ANALYST_L1, AML_ANALYST_L2, MLRO or FRONT_OFFICE for the user branch, ONBOARDING_SYSTEM for the app-only branch. Everything else refuses: a missing claim, a non-list (a single string included), an empty list, two or more elements (duplicates included), a non-string element, an empty string.
- **Actor and centre:** as v6 6 step 4. To confirm in the tenant: `azp`, `scp`, `idtyp`, `roles`, `oid`, `tid`.
- **Test 18.5 (complete).** User token: `[FRONT_OFFICE]` accepted; `[ONBOARDING_SYSTEM]`, `[MLRO, OTHER_APPLICATION_ROLE]`, `[MLRO, AML_ANALYST_L1]`, `[MLRO, MLRO]`, `[""]`, `[aml_analyst_l1]`, `[]`, `"MLRO"` (a single string), `[1]`: each 401. User token with `scp` and no `roles`: 401. User token with an unregistered `azp`: 401. User token with an onboarding `azp`: 401. `azp` differing in case: 401. App-only token: `[ONBOARDING_SYSTEM]` with the registered centre accepted; `[ONBOARDING_SYSTEM, OTHER_APPLICATION_ROLE]`, `[ONBOARDING_SYSTEM, ONBOARDING_SYSTEM]`, `[AML_ANALYST_L1]`: 401; app-only with `scp` present (`"scp": ""`): 401; app-only with `"roles": "ONBOARDING_SYSTEM"` (a single string): 401; app-only token with the BFF's `azp`: 401.

## 7. Secrets (F7, D26)

- **Secrets:** DATABASE_PASSWORD, FLYWAY_PASSWORD, SERVICE_TLS_KEYSTORE_PASSWORD and CLIENT_CA_TRUSTSTORE_PASSWORD, bound to `app.secrets.*` (v6 7.2). The other 18 variables keep the per-field `@NotBlank` and `@Pattern` of v6 7.2.
- **Why secrets differ.** Boot echoes a rejected value. `BindValidationFailureAnalyzer.appendFieldError` writes `Value: "%s"` from `FieldError.getRejectedValue()`, and `BindValidationException.getMessage` lists each error, whose `toString` carries the rejected value (verified in `spring-boot-4.1.2.jar`). A constraint on the value of a secret would print it at startup whenever it failed (for example a real password containing `${`).
- **Check.** Each secret has `@AssertTrue(message = "app.secrets.database-password (DATABASE_PASSWORD) must be set: the variable is unset or empty") boolean isDatabasePasswordSet()`, true when the value is non-null, not blank and contains no `${`. The rejected value is then `false`. Stage 3 confirms that the analyzer output and the exception message hold no secret.
- **`toString`** of the secrets record is overridden to `Secrets[values not shown]`. The enclosing record prints that.
- **Deployment check:** no secret value contains `${`. Boot would try to resolve it as a placeholder in any case.
- **Tests 18.6s:** each secret set to `pa${ss` is refused, and neither the failure report nor any cause message contains `pa${ss`; `toString` of the record contains none of the four test values.

## 8. Decoder and validators (F9, F12)

- **Corrected facts (spring-security-oauth2-jose 7.1.2).** The `NimbusJwtDecoder(JWTProcessor)` constructor sets `JwtValidators.createDefault()` (offset 26), which is `JwtTypeValidator.jwt()`, `new JwtTimestampValidator()` and `X509CertificateThumbprintValidator`, not timestamps only. `createDefaultWithIssuer(issuer)` is `createDefaultWithValidators(new JwtIssuerValidator(issuer))`, which adds those three when absent. The `JwtTimestampValidator()` constructor sets `allowEmptyExpiryClaim` and `allowEmptyNotBeforeClaim` to true (`iconst_1`), so the library accepts a token with no `exp`; `ConfiguredIdentityValidator` is what refuses it. `JwtTypeValidator.jwt()` accepts `typ` `JWT` or no `typ` (`setAllowEmpty(true)`). To confirm in the tenant: the `typ` of Entra access tokens, and that they carry no `cnf`.
- **Composition as static methods of `IdentityJwtDecoder`,** used by every chain and by the refusing decoder:

```java
static OAuth2TokenValidator<Jwt> libraryValidators(String issuer, String audience) {
    return new DelegatingOAuth2TokenValidator<>(
            JwtValidators.createDefaultWithIssuer(issuer),   // type, timestamps, x5t thumbprint, issuer
            new JwtAudienceValidator(audience));             // aud contains the audience
}
static OAuth2TokenValidator<Jwt> validators(String issuer, String audience,
        OAuth2TokenValidator<Jwt> configured, OAuth2TokenValidator<Jwt> application) {
    return new DelegatingOAuth2TokenValidator<>(libraryValidators(issuer, audience), configured, application);
}
```

- **Total by construction.** `ConfiguredIdentityValidator` and `ApplicationTokenValidator` read raw claim values with `instanceof` (6.3), call no conversion accessor, contain no `throw` (Checkstyle `noThrowNew`) and no catch-all, and return `OAuth2TokenValidatorResult` on every path. The library validators are not ours.
- **Defect path kept visible.** A `RuntimeException` from a validator is not caught by `validateJwt`, the provider or the filter, so it becomes a 5xx (v6 9.6). No catch-all is added. Test 18.12e documents it; whether the owner accepts it is section 15 item 4.
- **Tests:** 18.8b to 18.8d as v6, through `IdentityJwtDecoder`; **18.8e:** `libraryValidators` alone accepts a token with no `exp`, and `validators(...)` refuses it, which shows that the refusal comes from `ConfiguredIdentityValidator`; **18.8f:** `typ` `at+jwt` is refused and a missing `typ` is accepted by `libraryValidators`.

## 9. Key chain (F4, F8, F13)

### 9.1 Reference comparison (F13)

`ReferenceComparisonRefreshJWKSetEvaluator.requiresRefresh(set)` is true when `set == this.jwkSet` (`if_acmpne` at 5 jumps to `iconst_0`). The cache is refreshed when it still holds the set the caller rejected. v6 stated the opposite polarity, and its consequence too: a valid cache with an unknown `kid` **does** ask for a refresh. `JWKSetBasedJWKSource.get` asks with `noRefresh()` and, when no key matches, again with `referenceComparison(set)`; `CachingJWKSetSource.getJWKSet` passes that evaluator to `loadJWKSetBlocking` (offsets 32 to 49), and `loadJWKSetNotThreadSafe` caches the exact instance the source returned (offset 19). The fetch then goes through the limiter.

**Requirement:** the serving layer returns `record.keys`, the same instance the cache holds, unchanged. A copy would make every reference comparison false, and no unknown `kid` would ever cause a refresh. **Test 18.16:** an unknown `kid` with a valid cache causes exactly one IdP request, and the new key verifies.

### 9.2 Waiters and the refresh timeout (F8)

- **Refresh timeout: 5 000 ms**, a named constant in code passed to `CachingJWKSetSource(source, ttl, refreshTimeout, listener)`, replacing Nimbus's 15 000 ms default. It covers one fetch (the connect and read timeouts of 2 000 ms each in `BearerTokenSecurityConfiguration`) and is well under 300 s.
- **No IdP request by the waiter: only on the lock-timeout path** ("Timeout while waiting for cache refresh", `JWKSetUnavailableException` at 387) **and the interrupt path** (490).
- **A waiter that obtains the lock re-checks** (offsets 210 to 232). If the cache is empty, or still holds the set it was asked about, the waiter calls the source itself (274). That is its own IdP request through the limiter, and its own `fetchFailed` if it fails. "Unable to refresh cache" (472) arises when the lock was obtained, no reload was required, and the entry is not valid at the caller's `now`. It is not counted.
- **Catch clauses:** as v6 9.2.
- **Test 18.12f (empty-cache waiter):** no set has ever been fetched; the IdP is slow (1 s) and fails; X fetches; Y waits and obtains the lock after X's failure. Assert two IdP requests (X's and Y's), two `fetchFailed` calls, one WARN (UNKNOWN to FAILING) and both answers 401. 18.12b keeps the lock-timeout case (IdP slower than the timeout) and the interrupt case: no IdP request by the waiter, no `fetchFailed`.

### 9.3 Pair first, then the clock (F4, D25)

```
getJWKSet(evaluator, now, ctx):
  try { source.getJWKSet(evaluator, now, ctx); } catch ... as v6 9.2
  pair = health.current();                           // one read of (record, state), first
  t = clock.millis();                                // then the clock
  if (pair.record == null) return EMPTY;
  if (t - pair.record.fetchedAtMillis >= windowMillis) { health.expire(pair); return EMPTY; }   // CAS on that pair
  return pair.record.keys;
```

Reading the clock after the pair means a record's age is never understated, however long the thread waited in between. The window can only close early, never late (D-21). The cost: a thread that read an older pair can serve that older set once more inside its window. Clock-first, which v6 used, could serve a record past 300 s after a long wait between the clock and the pair.

Setup for 18.1 to 18.1c: S1 fetched at 0 (kid K1), TTL 60 000, window 300 000. Every test passes `now` and a test `Clock` explicitly.

- **18.1 (concurrent).** X calls with now 10 000, gets the cache hit, reads the pair (S1, 0) and blocks in the test clock before its clock read. Y calls with now 60 000, refreshes to S2 (K2) and stores (S2, 60 000, OK). **The IdP fails every fetch after Y's.** X is released and its clock reads 60 000: age 60 000 is under 300 000, so X answers S1 and K1 verifies for X. Every request that reads the pair after Y's store answers S2, and K1 is refused for it. K2 verifies at 359 999 and is refused at 360 000. Two successful fetches in total.
- **18.1a (sequential):** as v6.
- **18.1c (the bound).** No Y. X reads (S1, 0) and blocks until its clock reads 300 000. X answers EMPTY (401), its CAS moves OK to LAPSED, and one LAPSED WARN is written.
- **18.1b:** as v6 (forced refresh; times chosen for the limiter). The evaluator facts it cites are now correct (9.1).

## 10. D-20 residual: two options for the owner (F2)

Today a certificate from the trusted CA with an unregistered subject completes the handshake and gets the constant 401 at HTTP (18.9(c)). D-20 says only the BFF and onboarding may open a connection. The architect does not choose.

**Option A: amend D-20.** "May open a connection" becomes "is identified only with a registered certificate". The handshake checks the CA, HTTP checks the subject (zero key fetches, constant 401), and the CA issues only these certificates (deployment check). No code beyond v6.

**Option B: subject check at the handshake.** A `TomcatConnectorCustomizer` bean runs after Boot's `SslConnectorCustomizer`, which sets `setCertificateKeystore` and `setTrustStore` from the bundle (verified). For each `SSLHostConfigCertificate` it calls `setSslContext(...)` with an implementation of Tomcat's public interface `org.apache.tomcat.util.net.SSLContext` (8 methods, verified). That implementation wraps a JSSE `SSLContext` built from the bundle's `SslManagerBundle.getKeyManagers()` and a `SubjectCheckingTrustManager`. The trust manager delegates to the bundle's trust manager, then compares the leaf's issuer and subject as `X500Principal` with the registrations. `AbstractJsseEndpoint` uses a configured `getSslContext()` before generating its own (verified calls). Consequences:
- An unregistered subject fails the handshake: no HTTP exchange, no log line from the application. 18.9(c) becomes "handshake refused"; the resolver check stays as a second guard.
- **A trust manager refuses only by throwing `CertificateException`.** That needs `throw new` in `src/main`, which Checkstyle `noThrowNew` bans, with no escape left. Option B therefore needs an explicit, scoped exception to a hard ban, decided by whoever owns the bans. The architect does not work around a gate (copilot section 1).
- Tomcat's own implementation, `jsse.JSSESSLContext`, is package-private (verified), so the wrapper is hand-written; copilot 0.7 requires the comment naming it. Stage 3 confirms that the bundle's trust manager is an `X509ExtendedTrustManager` and that TLS 1.3 reports the refusal to the client.
- Rejected variant: `SSLHostConfig.setTrustManagerClassName`. `SSLUtilBase` instantiates the class through its public no-argument constructor and uses it as the only trust manager (verified), so it cannot receive the registrations from Spring configuration and would have to load the CA itself.

## 15. Decision requested

What the product owner must still decide:

1. **D-22 consequence.** The decision log cannot show success, and failed decisions (503 and 504 included) are invisible to operations. Amend D-22 to allow a coarse outcome, or accept the gap.
2. **D-20.** Option A (amend D-20: the handshake checks the CA, HTTP checks the subject) or option B (handshake-time subject check, which needs a scoped exception to the `throw new` ban) (section 10).
3. **Container 400 for malformed `Content-Length`** at the BFF and the service, before identification (section 3.3). Confirm it as LOW, like Tomcat's refusal of an oversized header. No application-level alternative exists that judges nothing.
4. **Validator defect gives 5xx.** Accept that a defect in a validator answers 5xx rather than 401 (no catch-all is allowed), or name another treatment (section 8).
5. **BFF dependency decision.** The Redis client, the session store and the Entra client; none is in `pom.xml` (the forwarding client is the JDK's).
6. **Quarantine release role** (D-18, BR-46).
7. **One live session per user.**
8. **Session lifetimes:** idle and absolute timeouts. The absolute timeout is also the retired-key period (section 5).
9. **Logout:** local only, or also revoke the user's refresh tokens at Entra.
10. **Owner of the BFF:** code, Entra registration, certificates and Redis.
11. **BFF in this increment,** or the service side only.
12. **Log fields on the risk read routes:** the decision-route set, or the template and status as well.
